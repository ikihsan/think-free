# Tasks

Dispatchable units of work. One Markdown file per task, each declaring a
**runnable verification command** so completion is decided by evidence rather
than by an agent's confidence.

Protocol: [`../docs/process/task-lifecycle.md`](../docs/process/task-lifecycle.md).
Skill: [`task-execution`](../.agents/skills/task-execution/SKILL.md).
Map: [`INDEX.md`](INDEX.md) (generated).

## Using them

```bash
tools/origin task list
tools/origin task new --goal "…" --verify "tools/origin doc lint"
tools/origin task claim T-0001 --agent "$AGENT" --vm "$(hostname)"
tools/origin task verify T-0001
tools/origin task complete T-0001 --summary "…" --evidence …
tools/origin task cancel T-0001 --reason "…"
```

Statuses: `open`, `claimed`, `blocked`, `done`, `cancelled`.

## Files

| File | Mutability | Contents |
|---|---|---|
| `T-NNNN-slug.md` | Hand-edited by whoever works the task | Goal, rationale, preconditions, steps, acceptance criteria, verification, rollback, notes |
| `CLAIMS.jsonl` | **Append-only. Never hand-edited.** | Every claim, completion, and cancellation, in order |
| `INDEX.md` | Generated | Status table, regenerated by `origin doc index` |

## The verification command

The most important field in a task file. It must exit non-zero when the work is
not done, run from the repository root, and cover everything the acceptance
criteria require.

`tools/origin task verify T-0001` runs it, prints the tail of the output on
failure, and exits `3` when the command ran and failed. Exit `1` means the task
has no `verify` field, which is an authoring error.

A task whose verification cannot fail is worse than no task: it produces false
completion signals at fleet scale.

## Concurrency

Git is the only shared state. A claim is one appended line in `CLAIMS.jsonl`, so
two agents on different branches appending different lines merge cleanly, and a
claim cannot be silently overwritten. A second agent claiming a held task fails
with exit `1` and names the holder.

Stale claims from a departed VM are possible. Take over honestly: finish the dead
session first with `origin session finish`, then claim with a note recording the
takeover. See [`../docs/process/session-protocol.md`](../docs/process/session-protocol.md)
for the recovery sequence.

## What a task is not

A task says what to do. Findings belong in `HYPOTHESES.md`, `FAILURES.md`,
`DECISIONS.md`, or an `EXPERIMENTS/` directory, tied to the session that produced
them. Findings recorded only in a task file are lost when the task is closed.
