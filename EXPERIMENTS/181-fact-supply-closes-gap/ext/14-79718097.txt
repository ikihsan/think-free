TITLE: Why do C compilers still prefer PUSH over MOV for saving registers, even when MOV appears faster in llvm-mca?
TAGS: c,assembly,x86-64,compiler-optimization,micro-optimization
QUESTION AS POSTED:
I noticed that modern C compilers typically use `push` instructions to save caller-saved registers, rather than explicit `mov` + `sub` sequences. However, based on `llvm-mca` simulations, the `mov` approach appears more efficient in some cases. Why is this? 
 On Skylake , `push` shows a clear dependency chain in `llvm-mca` . I also tested this on AMD’s Zen 5 (znver5), where `push` performance approaches `mov` but remains slower, with the same dependency chain behavior. 
 I analyzed two ways to save caller-saved registers: 
 
 `push` sequence : 12x `push` instructions. 
 `mov` sequence : 12x `mov` to stack + 1x `sub rsp, 96` . 
 
 Using `llvm-mca` (Skylake model), the `mov` version shows better throughput: 
 
 Total cycles : 27 ( `push` ) vs 15 ( `mov` ). 
 uOps : 36 ( `push` ) vs 13 ( `mov` ). 
 IPC : 0.44 ( `push` ) vs 0.87 ( `mov` ).

COMMENTS ON THE QUESTION, in order:
- [U. Windl] If the claim is that `mov r, offs(%rsp)` is faster than a `push` , you should include the change of the stack pointer, too. Adding a value once after a block of moves is some way of cheating, because the compiler knows how many pushes were made. Also it seems the "move code" has problems with race conditions (like ISRs that may opush values, also).

- [Peter Cordes] @U.Windl: The x86-64 System V ABI has a red zone, 128 bytes below RSP which are guaranteed not to be asynchronously clobbered, e.g. by signal handlers. (Kernel code uses `-mno-red-zone` because interrupts are handled on the same kernel stacks that are in use while kernel code is running. In that case you'd simply use `subq $96, %rsp` before the `mov` stores, like you'd do in 32-bit code, or for the Windows x64 ABI, if you wanted to avoid `push` . Only downside is that `-128` fits in disp8 but `+128` needs a disp32. For the same reason, you can use `add $-128, %rsp` vs. `sub $128` )

- [Peter Cordes] @MartinKealey: Zero-latency store-forwarding is indeed a thing on recent Intel and AMD, at least for some special case; limitations depend on the CPU. web.archive.org/web/20230323133845/https://www.agner.org/for‌​um/… about Zen 2, and Travis Downs (BeeOnRope) commented there about Ice Lake having it, too. chipsandcheese.com/i/138977299/loadstore-unit says Golden Cove (Alder Lake P-cores) can do zero latency SF with "an exact address match", so no restriction on same addressing mode, just can't be e.g. store 16 bytes and load the top 4.
