=== TITLE ===
Conditional debug print speeds up code execution in sum of two squares problem

=== QUESTION ===
A debug print line seems to make code execution unexpectedly faster. Commenting out a prin
tf that is conditional on n<100 slows things down when n is much larger. 
 How is the conditional print that never executes for n>100 speeding things up? 
 This toy code arises from a question on Math SE What is the most efficient way to determi
ne if a natural number N can be written as the sum of two squares? . It is a surprisingly 
tough problem with a single thread unvectorised solution taking around 4 hours to count th
em out to 10 9 . 
 That question gives a naïve algorithm which is easy to check and asks if there is a faste
r way. I thought that avoiding multiplies and sqrt in the main loop would
speed it up even if it remains O(sqrt(N)). 
 This is my first attempt. The odd thing was that my initial routine with a debug print in
 for small n was actually faster than any of my later attempts to simplify and optimise it
 once I had it working. 
 The least subtle behaviour applying to both MSVC and Intel ICX compilers is that commenti
ng out a debugging conditional printf slows things down! In the case of Intel ICX 2025.2.1
 by almost 30% (MSVC by 2.5%). 
 I'm at a loss to explain this. Intel generated code is also notably faster than MSVC. I m
ay be missing something obvious. Timings table - power of 10 increase in N roughly increas

bool sum_2squares(unsigned int n)
{

 a2 = 0;
 delta_a = 1;
 b2 = limit * limit;
 delta_b = 2 * limit - 1;
 while (a2 <= n / 2)
 {
 sum = a2 + b2;
 if (sum == n) // solution
 {

 a2 += delta_a;
 delta_a += 2;
 if (sum > n)
 {
 delta_a -= 2;
 a2 -= delta_a;
 b2 -= delta_b;
 delta_b = delta_b - 2;
 }
 }
 return n == sum;
}

 UPDATE:
Guided by the disassembly and profiling I created a straightjacket to force the compiler t
o generate code that allocates 64bit and 32 bit variables in the same fashion as the faste
r conditional printf code. 
 This has worked in the sense that the resulting code is now faster 7s vs 11s and uncommen
ting the conditional printf line now adds 0.5s to the execution time. This is a useful res
ult but is by no means a satisfactory answer. The compiler by default is generating substa
ndard code for this admittedly strange branch dense code. The flaw appears to be in the co
mpilers register allocation algorithm and/or branch target destination(s) when the simpler
 code is presented to it. 
 This also allowed a tidy of the logic with advantage (previously the code was crippled if
 the addition to a2 was not in the outer loop. Original lines commented out below to show 
the changes made.

=== KEY ANSWER (highest scored) ===
Instead of polluting the issue with extra calls to printf in the inner loop, let's just ad
d some instrumentation to compute statistics. Here is a version that counts the number of 
tests: 
 #include <stdio.h>
#include <math.h>
#include <time.h>

unsigned long stats[4];
#define STAT(i) stats[i]++

#ifndef STAT
#define STAT(i)
#endif

bool sum_2squares(unsigned int n)
{
 unsigned int limit = (unsigned int)+sqrt(n);
 unsigned int a2, b2, delta_a, delta_b, sum = 0;
 a2 = 0;
 delta_a = 1;
 b2 = limit * limit;
 delta_b = 2 * limit - 1;
 sum = 0;
 while (a2 <= n / 2) {
 STAT(0);
 sum = a2 + b2;
 if (sum == n) { // solution
 STAT(1);
 return true;
 }
 a2 += delta_a;
 delta_a += 2;
 if (sum > n) {
 STAT(2);
 delta_a -= 2;
 a2 -= delta_a;
 b2 -= delta_b;
 delta_b = delta_b - 2;
 }
 }
 STAT(3);
 return sum == n;
}

int main()
{
 unsigned int count = 0;
 unsigned int limit = 10;
 time_t start, end;
 start = clock();
 for (unsigned int i = 1; i <= 10000000; i++) { // runtime about 20s (gets 30x slower
 if (sum_2squares(i)) count++;
 if (i % limit) continue;
 if (limit == 10) {
 printf("N count time/s");
 if (stats[0]) {
 printf(" total loops alternations matches non-matches");
 }
 printf("\n");
 }
 printf("%-9u %-9u ", i, count);
 end = clock();
 printf("%6.3f", (double)(end - start) / CLOCKS_PER_SEC);
 if (stats[0]) {
 printf(" %12lu", stats[0]);
 printf(" %12lu %5.2f%%", stats[2], stats[2] * 100.0 / stats[0]);
 printf(" %8lu %6.3f%%", stats[1], stats[1] * 100.0 / stats[0]);
 printf(" %8lu %6.3f%%", stats[3], stats[3] * 100.0 / stats[0]);
 }
 printf("\n");
 limit *= 10;
 }
}

 More code, yet almost twice as fast! 
 My guess is we have a pathological case of branch misprediction with too many branches in
 the same cache line: 
 
 the first test is almost always false (branch only taken in 0.044% of tests at 10 7 . 
 the second test is almost always false as well (branch taken except in 0.011% of tests at
 10 7 . 
 the third test (alternations) is true in 28% of cases, so mispredicted more than half the
 time. 
 
 If the same prediction hardware is used for the third test and the second or first one (w
hich may be duplicated at the end of the loop), the branch prediction is very ineffective.
 Smaller code resulting in more branch misprediction, hence slower execution times. 
 Branch prediction hardware is intrinsic to the actual hardware (Apple silicon M4-pro in m
y case) and the behavior also depends on the code produced by the compiler, not only which
 instructions are used but also and sometime predominantly its layout. 
 I am a bit surprised that the compiler would not ensure optimal code layout to avoid this
 pathological case of prediction interaction, but the timings seem to point to this explan
ation.
