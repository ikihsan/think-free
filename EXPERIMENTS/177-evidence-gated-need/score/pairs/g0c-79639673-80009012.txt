Neither POSIX nor C FAQ recommend such a thing. 
 There are no POSIX APIs that take T const * const * so there's no need to cast anything t
o such type as far as POSIX is concerned. The quoted passage from the POSIX document expla
ins why there are no such APIs, not what to do when you see one (there are none). 
 The quoted passage from the C FAQ doesn't mention such types at all. It does tell you tha
t if you need to pass a char** to a function that expects const char** you would need a ca
st. This is hardly a recommendation, given that it immediately warns you that the need for
 such cast likely indicates a deeper problem that the cast wouldn't fix. 
 It is true that casting T ** to T const * const * (or indeed to T const ** ) and using th
e resulting pointer (even without modifying anything) can lead to UB, but there are no rec
ommendations to use such casts by POSIX or C FAQ. 
 There is a problem of casting in the opposite direction though. Some APIs like execv expe
ct a char * const * . If for some ungodly reason all you have is char const * const * , yo
u need to cast (or copy the entire array, which to my limited knowledge nobody ever does).
 And this cast leads to the same sort of UB you describe. To clarify, the problem is an in
termediate pointer being accessed through an lvalue of a type that is not a qualified vers
ion of the type of the underlying pointer object (one is T* and another is T const* , and 
no matter which is which, it's UB). 
 It is sometimes suggested that since T* and T const* have identical representation and al
ignment requirements, it is somehow OK to perform such access. But the standard makes no p
rovision for that. 
 When programming in C, you shouldn't really be dealing with deeply qualified pointer type
s, precisely because they are broken and you cannot convert between those and nowhere-qual
ified pointers without UB. C and POSIX (to my knowledge) only use top-qualified multilevel
 pointers in their APIs so if you stick with their types, you should be fine. But the prob
lem is there and it is known. 
 When writing in C++ it is harder to escape the problem because string literals are const 
. But in C, just avoid deep const . 
 For array types the problem is solved in C23: array types now share qualification with th
eir element types, so you can now have multilevel const-qualified arrays and pointers to t
hose arrays behave consistently. Pointers to pointers remain a problem though.
